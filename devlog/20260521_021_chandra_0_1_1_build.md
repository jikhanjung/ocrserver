# 20260521_021 — chandra `:0.1.1` build + Hub push (KOPRI 호스트에서 성공)

## 동기

HANDOFF.md 와 020 에서 deferred 됐던 작업. wrapper 측이 `0.1.6` 까지 핀 동안
chandra 는 `:0.1.0` 그대로였고, 020 시점에서 KOPRI 호스트의 12% stuck 함정
때문에 외부 빌드 우회로로 보내려던 참이었음.

이번 세션에서 한 번 더 시도 → **이번엔 통과**.

신규 layer (3.55 / 2.08 / 1.73 GB 등) pull 부터 들어감.

## 12% stuck 함정에 대한 메모

CLAUDE.md "Known gotcha" 섹션에 적혀있는 것처럼, 직전 세션(020)에서
이 호스트의 `docker build` 가 snapshot_download 단계 12% (17 files 중 2번째)
근방에서 **두 번 연속** 같은 지점에 stuck. 그래서 외부 빌드 우회로를
권장 워크플로로 잡아둠.

이번 시도는 그 권장에도 불구하고 그냥 같은 호스트에서 돌려봤고 통과.
샘플 1회로 함정이 사라졌다고 결론 내리진 않음. 가설:

- 베이스 이미지를 새로 받으면서 buildkit 의 내부 상태가 리셋된 것이
  영향이 있을 수 있음 (직전 두 시도는 base layer 가 캐시에 있었던 상태
  에서 #7 만 새로 돌렸음).
- KOPRI 망 / WAF / SSL MITM 측의 일시적 컨디션 변화일 가능성.

**판단:** CLAUDE.md 의 "Known gotcha" 텍스트는 그대로 둔다. 다음 chandra
빌드가 또 12% 에서 멈출 가능성은 여전히 있고, 외부 빌드 우회로는 검증된
fallback. 다만 "일단 호스트에서 한 번 시도해보고 12% 에서 멈추면 kill" 의
"일단 시도해보는" 부분이 합리적이라는 추가 데이터포인트.

## 푸시

```bash
docker push honestjung/ocrserver:0.1.1   # 큰 layer 약 7GB 신규 push
docker push honestjung/ocrserver:latest  # 같은 digest, manifest 만 갱신
```

둘 다 same digest (`f6117fbbb2ca...`, size 856). Docker Hub
`honestjung/ocrserver` 의 `:0.1.1` + `:latest` 둘 다 이 digest 로 가리킴.
