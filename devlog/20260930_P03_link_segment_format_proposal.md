# P03 — link 답을 "캡션 구간" 형식으로: PaperMeister 에 제안

**작성**: 2026-09-30 · **대상**: PaperMeister(도판 파이프라인 ② link 단계) · **근거**: `docs/FIGURE_LINK_STALLS.md` §2·§5·§6
**실험 코드**: `scripts/experiments/link_segments/` (형식 설명·빌더·러너·복원기·비교기, README)

## 0. 한 줄 요약

> link 답에서 **캡션을 한 번만, 조각으로** 쓰게 하고 항목 설명은 클라이언트 스크립트가 조각에서 만든다.
> 운영 답과 같은 항목 10건을 세 차례(30회) 돌려 **출력 55–65%, 시간 65–75%, stall 0, 스키마 오류 0**.
> 가장 큰 항목들이 절반 안팎으로 줄어 끊김이 시작되는 15k 토큰 아래로 내려온다. 서버 변경은 거의 없다 — 프롬프트·스키마·복원이 클라이언트 몫.

## 1. 왜 — link 의 시간은 답의 길이다

link 응답 400건(항목 23,919개)을 o200k 토크나이저로 잰 결과:

- 출력 토큰의 **88.6% 가 최종 JSON**(사고 토큰 5.5%). 소요 ≈ **94 s + 1k 출력 토큰당 33.5 s, r = 0.96**. 쪽수와의 상관은 0.33.
- 최종 JSON 구성: 캡션 전문 32% · 항목 설명 31% · JSON 구조·공백 32% · 라벨류 4%.
- **같은 텍스트를 두 번 쓴다**: 항목 설명 구절의 89% 가 캡션에 글자 그대로 있고, 설명의 32% 는 앞 항목과 같은 머리말(종명 등)의
  반복이다 — 지금 지시문의 "공통 종명·시점·배율을 모든 항목에 합쳐 넣으라" 규칙이 만드는 반복.
- 끊김(stall)은 답이 길 때 생긴다(09-18 실측: 출력 5k 미만 실패 0, 15k 초과 18건 중 5건). 09-23 배치에서는 stall 14회로 하루 약 7.5 h 를 잃었고,
  같은 크기로 다시 내면 같은 자리에서 또 멈췄다(`79fa0b44`·`e0837de8`).

캡션 자체는 줄이면 안 된다 — 캡션 줄 중 OCR 텍스트에 그대로 있는 것은 48% 뿐이다(모델이 OCR 을 고치고 줄을 잇는다). 줄일 곳은
**캡션을 설명으로 다시 쓰는 몫**이다.

## 2. 제안하는 형식

도판마다 `caption` + `entries` 대신 `segs` 문자열 하나. 캡션을 읽는 순서대로 **한 줄에 한 조각**, 각 조각은 한 번만:

```
x :: Explanation of Plate 3
h1 :: Oistodus aff. breviconus Branson & Mehl, lateral views, x40.
e 1,2 | L=Figs. 1-2. | s=YSUG 00287; YSUG 00288 :: Hunghuayuan Formation.
h1 :: Drepanodus arcuatus Pander.
e 3 | L=Fig. 3. :: Posterior view, YSUG 00290.
e 4 | L=Fig. 4. | d=Drepanodus arcuatus Pander. Posterior view, YSUG 00291. :: Same, YSUG 00291.
t 3,4 :: Scale bar 100 μm.
```

| 조각 | 뜻 |
|---|---|
| `x` | 어느 항목에도 속하지 않는 캡션 텍스트 — 플레이트 제목, 패널 없는 그림의 캡션 전체, 조건부 주석 |
| `h1` / `h2` | 뒤따르는 항목들이 공유하는 머리말(종명·저자·시점·배율·산지, 또는 패널 있는 그림의 제목 문장) / 그 안의 소머리말 |
| `e <labels>` | 항목 하나. 범위는 펼친다(`e 1,2`). `L=` 인쇄 라벨(캡션에만 들어감) · `s=` 표본번호 · `d=` 드문 예외 설명(동상 "id." 해소 등) |
| `t` / `t <labels>` | 꼬리 주석 — 라벨이 있으면 그 항목들에, 없으면 마지막 `h1` 이후 항목 전부에 |

**복원(클라이언트 스크립트)**: 캡션 = 조각을 줄바꿈으로 이은 것(`L=` 포함, 원문 그대로). 항목 설명 = 열린 `h1` + `h2` + 항목 본문 +
해당 `t` (또는 `d`). `printed_label` = `L=`, 빈 `specimen_number` 는 빈 문자열. 결과는 **지금의 link 스키마와 똑같다** — 저장·검증·
`items_from_replies` 는 그대로 쓴다.

- 지시문: `scripts/experiments/link_segments/seg_format_proposed.md` (지금 link 지시문 끝에 덧붙임. v3 + `d` 남용 방지 한 줄)
- 스키마: 지금 스키마에서 도판의 `caption`·`entries` 를 `segs: string` 으로 바꾼 것(`build.py` 의 `compact_schema`)
- 복원기: `expand.py` (약 70줄, 의존성 없음). PaperMeister 쪽에 옮겨 쓰면 된다.

## 3. 실측 — 같은 10건, 세 차례

대상: 운영에서 이미 처리한 link 10건(출력 1.5k–27k 토큰, 모두 다른 논문). 운영 워커와 같은 codex 명령·작업 폴더·지시문(+ 형식 설명).

| | 시간 | 출력 토큰 | 최종 JSON | 설명 유사도(단어) | stall · 스키마 오류 |
|---|---|---|---|---|---|
| v1 | (9건) 74% | 65% | 58% | — | 0 · 0 |
| v2 | 65% | 55% | 50% | 0.81 | 0 · 0 |
| **v3** | **75%** | **65%** | **54%** | **0.88** | **0 · 0** |

큰 항목 예(v3): `bfa5311d` 644 → 394 s(출력 53%), `decfd5c7` 972 → 612 s(58%), `13e3464c` 936 → 596 s(55%).
같은 항목도 회차마다 시간이 꽤 다르다(`4a230ec8` 114 s / 180 s). 10건 표본에서 v2·v3 의 시간 차이는 형식 차이로 보기 어렵다.

**품질(v3)**: 도판·항목·라벨·표본번호가 운영 답과 거의 일치(표본번호는 숫자 기준 전부 일치). 차이는 아래 §4 의 결정 사항과
`d=` 남용 1건(`bc79da3f` — 러시아어 도판 а/б 하위 항목마다 이미 만들어지는 설명을 `d=` 로 42번 다시 씀, 출력 91%). 제안 형식은 이를
막는 한 줄을 넣었다(시험 전). 1차에서 한 번 나온 "설명 쪽을 못 찾고 전부 skip" 은 v2·v3 에서 재현되지 않았다(회차별 탐색 차이).

## 4. PaperMeister 가 정할 것

1. **라벨 없는 단일 그림의 항목**: 0개인가 1개(`"1"`)인가. 지금 운영 답 안에서도 논문마다 갈린다. 제안 형식은 0개(`x` 만).
   panels 의 `split_targets` 가 항목 2개 이상만 보므로 분할에는 영향이 없다.
2. **설명에 산지·쪽·층준을 넣을지**: 운영 답(A)은 종·시점·배율·표본번호만 남기고 산지("평양시 승호구역 광정리 운학층")나
   "с. 124 … зона …, слой 9" 를 빼는 경우가 있다. 구간 형식은 조각이 원문이라 이것들이 설명에 남는다. 원문에 더 충실하지만, 지금
   `description` 관례와 다르다. 남길지, 복원기에서 규칙으로 뺄지.
3. **전면 재처리 비용**: 프롬프트·스키마가 바뀌면 `prompt_version` 이 바뀌어 link 결과가 전부 다시 due 가 된다. 새 논문에만 적용하고
   기존 결과는 두는 방법(버전별 due 판정)도 있다.
4. **분할 무게 기준**: 답이 절반 안팎이 되므로 지금의 항목당 무게 상한(플레이트 8 · 항목당 80)을 올려 항목 수를 줄일 수 있다 —
   항목당 고정비(~94 s)를 덜 낸다. 다만 끊김 안전선(출력 15k)을 기준으로 다시 잡을 것.

## 5. 적용 순서 제안

1. 새 link 프롬프트 버전으로 `seg_format_proposed.md` 를 덧붙이고, 스키마를 `segs` 로.
2. 수거(collect) 때 `expand.py` 로 복원한 뒤 지금의 `validate_link_result` 를 그대로 태운다.
3. 파일럿: 이미 link 결과가 있는 논문 몇 편에 새 버전을 내 구버전 답과 대조(항목·라벨·표본번호·설명). 이 저장소의 `compare.py` 방식 참고.
4. 괜찮으면 새 논문부터 적용, 기존 결과의 재처리 여부는 §4-3 결정에 따라.

## 6. ocrserver 쪽 변경

- **필수 아님**: 서버는 요청에 실린 스키마로 구조만 검사하므로 그대로 동작한다. 워커도 그대로.
- **표시만**: 큐 페이지 `/figures` 의 link 결과 요약(`wrapper/figures.py` `_result_summary`)이 `entries` 를 세서, 구간 형식 답은 항목 0개로
  보인다. `segs` 가 있으면 `e ` 줄의 라벨 수를 세도록 고치면 된다 — 적용이 정해지면 ocrserver 에서 처리.
