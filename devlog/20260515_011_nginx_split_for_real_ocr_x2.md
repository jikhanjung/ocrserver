# 20260515_011 — nginx 설정 분리: 진짜 OCR×2 활성화

## 발견한 버그

`mode-ocr.sh`는 chandra-b 컨테이너를 띄우긴 했지만 **nginx upstream에 chandra-b를 추가하지 않아서** 모든 OCR 요청이 chandra-a 한 곳으로만 갔음.

```nginx
upstream chandra {
    server chandra-a:8000;     # chandra-b 없음
    keepalive 16;
}
```

결과: 5월 13일 운영 세팅 이래 OCR 모드가 사실상 동작 안 했음. chandra-b는 GPU 1을 점유한 채 놀고, 클라이언트 OCR_CONCURRENCY=12로 보내도 chandra-a에서 6개만 동시 처리되고 나머지 6개는 chandra-a 큐에서 대기.

`/api/stats`가 `recommended_concurrency=12`로 잘못된 값을 알려주는 것도 이 때문 — wrapper는 OCR_BACKENDS health 프로브로 alive=2를 보고하지만 실제 트래픽은 nginx에 막혀 chandra-a 단일 처리.

## 왜 단순 fix가 안 됐나

가장 간단한 해법은 nginx.conf에 chandra-b를 항상 적어두는 것:

```nginx
upstream chandra {
    least_conn;
    server chandra-a:8000;
    server chandra-b:8000;
}
```

근데 LLM 모드에선 chandra-b 컨테이너가 docker-compose profile에 없어서 docker network에 존재하지 않음. nginx는 startup-time에 upstream의 모든 server를 DNS resolve하고, 실패하면 시작 자체가 안 됨:

```
nginx: [emerg] host not found in upstream "chandra-b"
```

같은 이유로 `proxy_pass http://llm:8000/`도 LLM 컨테이너가 stop 상태면 nginx 시작 실패. (literal hostname을 쓰는 `proxy_pass`도 startup에서 resolve함, upstream과 동일)

## 해법: 두 config 분리 + mode 스크립트가 swap

```
nginx.llm.conf   # chandra-a only + /llm/ proxy
nginx.ocr.conf   # chandra-a + chandra-b (least_conn), /llm/ 없음
nginx.conf       # generated by mode-*.sh (gitignored)
```

각 mode 스크립트가 cp해서 활성화 + nginx 리로드:

```bash
# mode-ocr.sh
cp nginx.ocr.conf nginx.conf
docker compose exec nginx nginx -s reload || \
    docker compose up -d --no-deps --force-recreate nginx
```

`reload`로 안 되는 경우(컨테이너 시작 옵션 변경 등) recreate fallback. 실제로 오늘 첫 시도에서 reload는 작동했는데, /llm/ block 때문에 재시작 시 시작 실패하는 케이스가 있어 nginx.ocr.conf에서 /llm/ block을 빼는 별도 수정 필요했음.

## chandra-b 콜드 스타트 race condition 방지

기존 mode-ocr.sh는:
1. chandra-b up
2. wrapper recreate (즉시)
3. nginx reload (즉시)

이 순서면 nginx가 chandra-b로 라우팅하는 시점에 vLLM이 아직 로딩 중이라 502 → wrapper retry. 새 순서:

1. chandra-b up
2. **chandra-b health 대기** (`until curl -sf http://localhost:8000/health; do sleep 5; done`, ~4-5분)
3. nginx reload (이제 안전하게 분산)
4. wrapper recreate (OCR_CONCURRENCY=12 적용)

대기 동안 기존 chandra-a는 그대로 서비스 — 다운타임 없음.

## 검증

```
$ curl -s http://localhost:8080/api/stats | jq '{mode, ocr_backends_alive, recommended_concurrency, concurrency}'
{
  "mode": "2ocr",
  "ocr_backends_alive": 2,
  "recommended_concurrency": 12,
  "concurrency": 12
}
```

이제 단일 PDF여도 페이지 수 ≥7이면 nginx least_conn이 두 backend로 분산하고 두 GPU 모두 활용. 페이지 수 < 7이면 자연스럽게 한쪽에 몰림 (단일 PDF의 throughput 한계).

## 사용법 변경

- `nginx.conf`는 더 이상 직접 편집/git 추적하지 않음. `.gitignore`에 추가
- 변경 시 `nginx.llm.conf` 또는 `nginx.ocr.conf` 둘 중 하나를 수정하고 deploy 후 mode 스크립트 재실행
- 두 파일에 공통인 부분(wrapper proxy, /api/, /ocr 등)은 양쪽에 동일하게 유지 필요. 향후 envsubst나 include로 정리 여지 있음
