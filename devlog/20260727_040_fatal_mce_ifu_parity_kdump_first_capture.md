# devlog 040 — kdump 첫 실전 캡처: 프리즈의 정체는 CPU IFU 패리티 에러

날짜: 2026-07-27
태그: 인시던트 조사 (**프리즈 원인 확정 — CPU 내부 패리티 에러**),
038·039 결론 정정
선행: [devlog 038](20260727_038_silent_freezes_and_kdump_enablement.md) (kdump 복구),
[devlog 039](20260727_039_enginecore_segfault_memory_corruption.md) (세그폴트 조사)

## 요약

038 에서 복구해 둔 kdump 가 **설치 당일 오전 첫 실전 프리즈를 그대로
캡처**했다. 이번에는 추측이 아니라 커널이 남긴 사인이 있다.

**Fatal Machine Check Exception — Bank 0 (IFU), internal parity error,
PCC=1.** 즉 **CPU 코어 내부에서 명령어 인출 경로가 깨진 것**이고,
DRAM 에러가 **아니다** (`ADDRV=0` — 연관 메모리 주소 자체가 없음).

그리고 같은 날 오전, 세그폴트 쪽에서도 결정적 데이터가 나왔다.
**설정이 40여 회 재시작 내내 완전히 동일한데 크래시율이 3일 전부터
9배로 뛰었다.** 정적 소프트웨어 버그로는 설명이 안 되는 변화다.

**결론: 039 가 분리했던 두 문제를 다시 하나로 합쳐야 한다.
열화 중인 CPU 라는 단일 기질이 프리즈와 세그폴트를 모두 설명한다.**

이 문서는 038·039 의 결론을 둘 다 수정한다:

- **038**: 프리즈 주 용의자를 "호스트 RAM / DIMM 불량" 으로 두고 있었다
  → **배제**.
- **039**: 세그폴트 주범을 "AWQ/Marlin 커널" 로 좁혀 판별 실험을 설계했다
  → **철회**. 아래 5·6절.

## 2. 사인 — vmcore dmesg 링버퍼 마지막 9줄

`.crash` 의 `VmCoreDmesg` 를 풀면 1,755줄이 나오고 그 끝이 전부다.
직전까지는 UFW BLOCK 로그뿐 — **경고도 전조도 없이 한 방에 갔다.**

```
[14210.318765] mce: [Hardware Error]: CPU 4: Machine Check Exception: 5 Bank 0: b200000000070005
[14210.318768] mce: [Hardware Error]: RIP !INEXACT! 33:<00005be78e87b08b>
[14210.318771] mce: [Hardware Error]: PROCESSOR 0:50654 TIME 1785143002 SOCKET 0 APIC 8 microcode 2007006
[14210.318775] mce: [Hardware Error]: Machine check: Processor context corrupt
[14210.318776] Kernel panic - not syncing: Fatal machine check
```

`MCi_STATUS = 0xb200000000070005` 디코드:

| 필드 | 값 | 의미 |
|---|---|---|
| VAL | 1 | 유효한 에러 기록 |
| UC | 1 | **정정 불가 (uncorrected)** |
| PCC | 1 | **Processor Context Corrupt** — 복구 불가, 패닉 외 선택지 없음 |
| **ADDRV** | **0** | **연관 메모리 주소 없음** |
| MISCV | 0 | MISC 레지스터 정보 없음 |
| MCACOD | 0x0005 | **internal parity error** |
| MSCOD | 0x0007 | 모델 고유 코드 |
| Bank | **0** | Skylake-X 에서 **IFU (Instruction Fetch Unit / L1I)** |

부가:

- `RIP CS=0x33` → **유저스페이스 64bit 코드 실행 중** 발생
- `PROCESSOR 0:50654` → family 6 / model 0x55 / stepping 4 = Skylake-X
- 패닉 09:03:22 (uptime 14210s). journald 마지막 기록은 09:02:42 —
  40초 공백이 있으나 그 사이 로깅할 이벤트가 없었을 뿐일 수 있어
  과잉 해석하지 않는다.

### 왜 "DRAM 아님" 인가

`ADDRV=0` 은 **에러에 연관된 물리 주소가 존재하지 않는다**는 뜻이다.
DRAM 에러라면 메모리 컨트롤러 뱅크에서 올라오고 주소가 실린다.
Bank 0 은 코어 내부 명령어 인출 유닛이고, 여기 패리티 에러는
**L1 명령어 캐시에서 읽어온 비트가 깨졌다**는 의미다. EDAC 도 이 기간
내내 아무 에러를 올리지 않았다.

→ **039 의 "DIMM 4장 중 1장 미인식" 은 프리즈 원인이 아니다.**
(미인식 스틱은 주소공간에 없어 무해하다는 점은 039 에도 적었고,
이번 증거가 그걸 확정한다.)

## 3. 과열인가 — 로그상 근거 없음, 단 완전 배제 불가

```
Package id 0 = 47C     (max 89C, crit 99C, Tjmax 100C)
"temperature above threshold" / 클럭 스로틀 이벤트: 전 부팅 통틀어 0건
CPU max MHz 4500 = i7-7820X 의 Turbo Boost Max 3.0 정격 (오버클럭 흔적 없음)
```

부팅마다 grep 에 걸리는 "thermal" 7건은 전부 governor 등록 메시지지
온도 이벤트가 아니다. **판정: 고전적 과열(Tjmax 도달)은 아니다.**

배제 못 하는 부분:

- MCE 는 순간 이벤트다. 찰나의 Vcore 새그는 스로틀 로그를 안 남긴다.
- `gigabyte-wmi: No temperature sensors usable` — **VRM·보드 온도는
  아예 관측 불가.** 코어 온도만 보고 있다.

## 4. 하드웨어 실체

| 항목 | 값 | 왜 문제인가 |
|---|---|---|
| CPU | **Intel Core i7-7820X** | Xeon 이 아니라 **소비자용 HEDT**. 8C/16T, 소켓 1개 |
| 이력 | 중고로 들여온 것 | 과거 오버클럭에 의한 열화(electromigration)가 실재하는 시나리오 |
| 보드 | X299 AORUS Gaming 3 Pro-CF | |
| **BIOS** | **F1 / 2017-07-04** | **출시 당일 펌웨어, 9년째 그대로.** Skylake-X 의 AVX-512 전압/오프셋 안정성 수정이 전혀 안 들어가 있음 |
| microcode | 0x2007006 | 이건 비교적 최신. OS 가 부팅 시 로드 |

IFU 패리티 에러는 전형적으로 **마진이 부족한 코어**의 증상이다.
"중고 HEDT + 출시 초기 BIOS + AVX-512 워크로드" 는 교과서적 조합이다.

> 039 에서 "BIOS F1/2017" 을 **메모리 트레이닝 미숙** 맥락으로 적었는데,
> 이번 증거를 보면 같은 사실이 **CPU 전압 안정성** 맥락에서 훨씬 중요하다.
> 같은 관측, 다른 함의.

## 6. 039 결론 철회

039 는 세그폴트 주범으로 **AWQ/Marlin 커널**을 1순위에 올리고
`--quantization awq` 판별 실험을 다음 작업으로 잡았다. **철회한다.**

039 의 핵심 근거는 "14B → 32B-AWQ 전환 후 정규화해도 6배" 였는데,
그 비교는 **모델 교체 시점(06-24)과 하드웨어 열화 시점이 구분되지
않는다**는 약점이 있었다. 이번 데이터가 그 구분을 만들어준다 —
**모델은 06-24 이후 안 바뀌었는데 크래시율은 07-25 에 또 한 번 뛰었다.**
Marlin 커널로는 이 두 번째 점프를 설명할 방법이 없다.

| 관측 | Marlin 커널 버그 | **열화 중인 CPU** |
|---|---|---|
| 무관한 12곳에서 SIGSEGV | 설명함 | 설명함 |
| `THPVariable_clear` refcount assert | 설명함 | 설명함 |
| 입력과 무관 | 설명함 | 설명함 |
| 32B 전환 후 정규화 6배 | 설명함 | 설명함 (`--enforce-eager` × 레이어수 40→64 → 호스트 CPU 명령어량 급증) |
| **설정 불변인데 07-25 부터 9배** | **설명 못 함** | **설명함** |
| **Fatal MCE Bank 0 IFU** | **설명 못 함** | **설명함** |
| 프리즈와 세그폴트가 같은 시기에 동반 악화 | 설명 못 함 | 설명함 |

**039 의 "프리즈와 세그폴트는 별개 문제" 분리는 무효화한다.**
하나의 결함 CPU 가 두 증상을 모두 낸다고 보는 것이 가장 단순하고
증거에 부합한다. 프리즈는 커널 모드에서 잡혀 MCE 로 기록됐고,
세그폴트는 유저스페이스에서 손상된 결과가 파이썬 힙에 나타난 것이다.

> 참고로 이번 MCE 도 `RIP CS=0x33` 으로 **유저스페이스 실행 중** 발생했다.
> 같은 결함이 운 나쁘면 PCC=1 로 커널을 죽이고, 운 좋으면 프로세스만
> 죽인다 — 관측된 두 증상의 비율과 부합한다.

## 7. 조치 — rasdaemon 도입

정정 가능한(correctable) MCE 를 상시 기록하기 시작했다. 이전까지는
mcelog 도 rasdaemon 도 없어 **치명적 에러 직전까지의 전조 스트림을
통째로 못 보고 있었다.**

```bash
sudo apt install rasdaemon
sudo systemctl enable --now rasdaemon
```

09:16 설치, `active` / `enabled` 확인. DB 는
`/var/lib/rasdaemon/ras-mc_event.db` (world-readable, sudo 불필요).

**첫 관측 결과 — 09:16~10:05 약 50분간 `mce_record` 0건.**
그 사이 세그폴트가 2회 있었는데도 MCE 는 안 잡혔다. 해석은 보류한다:

- 정정 가능한 IFU 패리티는 하드웨어가 재인출로 조용히 넘길 수 있고,
  CMCI 설정에 따라 뱅크에 로그를 안 남길 수도 있다.
- 관측 50분은 결론 내기에 너무 짧다. 프리즈 간격이 4~13시간이다.

**알려진 걸림돌**: `ras-mc-ctl --errors` 가 `signal_event` 테이블 조회에서
스키마 불일치로 죽는다 (`no such column: signal`). MCE 항목 자체는
정상 출력된다. 필요하면 DB 직접 조회:

```bash
sqlite3 -header /var/lib/rasdaemon/ras-mc_event.db \
  "select * from mce_record order by id desc limit 20;"
```

## 9. 남은 관측 사각지대

- **dbgsym 여전히 미공개** — `linux-image-7.0.0-28-generic-dbgsym` 이
  ddebs 에 아직 없다 (038 에서 저장소는 등록). `crash` 유틸은 설치돼
  있으나 심볼 없이 열어야 한다. 이번 건은 MCE 라 dmesg 만으로 결론이
  났지만, 다음 건이 커널 Oops 면 심볼이 필요하다.
- **VRM/보드 온도 관측 불가** (`gigabyte-wmi: No temperature sensors usable`).
- **GPU ECC 두 장 다 Disabled** (039 지적, 그대로).
- **07-23 이 변곡점 근처** — 037(nvidia 드라이버 불일치 / unattended
  upgrade) 조치가 07-23 에 있었고, 크래시 폭증은 07-25 부터다.
  드라이버 변경이 호스트 파이썬 힙 손상과 CPU Bank 0 MCE 를 동시에
  일으킨다고 보기는 어려우나, **시점이 가깝다는 사실은 기록해 둔다.**
