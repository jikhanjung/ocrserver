# 도판 link 항목의 stall — 관찰과 판단 재료

도판 분할 워커(`scripts/figures_worker.py`, systemd `ocrserver-figures-worker`)가
link 항목에서 **codex 출력이 끊긴 채 멈추는(stall)** 현상을 정리한다. 원인 분석의
1차 기록은 devlog 047(스트림 끊김 = 긴 답 생성 구간, KOPRI MITM 아님)에 있고, 이 문서는
2026-09-23 대형 배치에서 본 규모와 패턴, 그리고 서버에서 조절할 수 있는 것을 모은다.

## 한 줄 요약

> link 항목의 시간과 실패는 **답의 길이**가 정한다. 답이 길어지는 항목은 같은 크기로
> 몇 번을 다시 내도 같은 자리에서 멈춘다. 고치는 곳은 클라이언트의 분할이고, 서버에서
> 조절할 수 있는 것은 **멈춘 뒤 얼마나 기다리느냐(idle 감시)** 정도다.

## 1. 관찰 — 2026-09-23 link 배치

PaperMeister 가 09-23 00:39 UTC 에 link 165항목(99편)을 한 번에 제출했다(새 link 프롬프트
`link-v1-533479a75b9f`, reading set 적용). 22:31 UTC 시점:

| | |
|---|---|
| 진행 | done 59 · **failed 4** · processing 1 · queued 101 (+ 뒤에 들어온 18) |
| 처리율 | 05:26 → 22:20 에 41건 = **약 25분/항목** (간격 60 s 포함) |
| 최근 24 h 호출 | 76건 중 **59 ok** |
| stall | 하루 **14회**, 모두 `no codex output for 1800s`. 회당 약 32분 → **약 7.5 h 소모** |
| 남은 시간 | 119항목 × 25분 ≈ 50 h |

stall 난 항목은 거의 매번 **같은 항목이 연속으로** 멈췄다:

| 논문 (file_hash 앞 8자) | 묶음 | 도판 | reading set 쪽수 | 결과 |
|---|---|---|---|---|
| `78fef4fc` | 3/5 | 10 | 286 | failed (3회 stall) |
| `79fa0b44` | 1/8 | 18 | 104 / 291 | failed |
| `32f87220` | 2/2 | 25 | 109 | failed |
| `e0837de8` | — | 6 | 20 / 110 | failed |
| `856f27a6` | 2/5 | 10 | 113 | 3번째 시도 done — 항목 266, 출력 19k 토큰 |
| `5db85517` | — | 4 | 26 | 3번째 시도 done — 항목 134, 출력 13k 토큰 |

도판 4–6개짜리도 멈췄다. **도판 수가 아니라 항목 수(= 답 길이)** 가 원인이다.

## 2. 시간을 정하는 것은 답의 길이

재시도 없이 한 번에 끝난 link 112건(09-23 기준)에서 소요 시간과의 상관:

| 요인 | r |
|---|---|
| PDF 쪽수 | 0.33 |
| 열람한 쪽 수 (`pages_consulted`) | 0.27 |
| 요청 도판 수 | 0.37 |
| 입력 토큰 | 0.60 |
| 결과 항목 수 | 0.81 |
| **출력 토큰** | **0.87** |

회귀: **소요 ≈ 150 s + 1k 출력 토큰당 33 s**. 같은 논문 안에서도 항목 5개 묶음은 188 s,
항목 484개 묶음은 1,392 s(Barrande 231쪽). 모델은 PDF 전체를 읽지 않고 필요한 쪽만 열기
때문에, 쪽수는 입력 토큰을 조금 늘릴 뿐이다.

## 3. 멈춘 시도의 모양

stall 로 끝난 시도들의 codex 이벤트(`run/aN/events.jsonl`)를 보면:

- 대부분 **재연결 알림 4회**(`Reconnecting... n/5 (stream disconnected …)`) 뒤 조용해진다.
  codex 자체 재시도를 거의 다 쓴 상태에서 출력이 끊기고, 워커의 idle 감시가 1800 s 뒤에 끊는다.
- `78fef4fc`·`e0837de8` 는 세 번 모두 **명령 1개 실행 → 메시지 2개 → 재연결 4회 → 정지**로
  똑같다. 읽기는 끝났고 답을 쓰기 시작한 구간에서 멈춘 것.
- `32f87220` 은 재연결 알림 **없이** 명령 실행 뒤 조용해졌다(3회 모두). 끊김 알림도 없이 멈추는 경우가 있다.
- 반대로 재연결 3–4회를 겪고도 끝난 시도도 있다(1,222 s · 1,622 s · 2,692 s). 재연결 자체가 곧 실패는 아니다.

같은 크기로 다시 내면 같은 자리에서 멈춘다는 점이 핵심이다. **서버 resume 은 이 항목들을
살리지 못한다.** 클라이언트가 더 잘게(`--per-item`, 플레이트 1장 = 1항목까지) 나눠 재제출해야 한다.

## 4. 서버에서 조절할 수 있는 것

파이프라인의 조절(분할 무게, reading set, 큐 채우기, 검증)은 PaperMeister 몫이다.
서버에 남은 손잡이:

| 값 | 지금 | 이 문제에 대한 효과 |
|---|---|---|
| `FIGURES_IDLE_TIMEOUT` | 1800 s | stall 한 번에 버리는 시간. 줄이면 하루 7.5 h 손실이 줄어든다 |
| `FIGURES_SESSION_TIMEOUT_LINK` | 3600 s | 재연결을 반복하며 끝나지 않는 세션의 상한 |
| `FIGURES_MIN_INTERVAL` | 60 s | link 에서는 전체 시간의 ~5%. 영향 작음 |
| 워커 동시 처리 수 | 1 | 처리량의 유일한 지렛대. codex 구독 토큰 한도와 맞물려 **검토사항**(HANDOFF) |

### idle 감시를 줄일 수 있나

이력: 09-17 에 900 s 로 시작 → 긴 논문의 최종 JSON 생성 구간을 stall 로 오판해 정상 답을
버린 뒤 **1800 s** 로 올렸다(devlog 047).

이번 배치에서 정상 완료된 항목 중 가장 긴 것은 총 2,692 s 였지만, **그 안에서 출력이 가장 오래
끊겼던 구간이 몇 초였는지는 알 수 없다.** `events.jsonl` 의 이벤트에 시각이 없어서다.
그래서 지금은 900–1800 사이 어느 값이 안전한지 근거가 없다.

판단하려면 먼저:

1. **워커가 이벤트 줄마다 받은 시각을 남기게 한다** (예: 별도 `events.ts` 에 `monotonic` 오프셋).
   codex 출력 형식은 그대로 두고 워커 쪽에서만 기록.
2. 며칠 모아 **정상 완료 시도의 최장 무출력 구간** 분포를 본다.
3. 그 최대값에 여유를 둔 값으로 `FIGURES_IDLE_TIMEOUT` 을 정한다. 필요하면 "재연결 알림
   n회 이후"처럼 조건부로 짧게 끊는 방식도 이 데이터로 검토한다.

## 5. 답을 줄일 여지 — 출력 토큰의 구성

link 답은 도판마다 `figure_id`·`name`·`caption`(인쇄된 캡션·설명 전문)·`caption_source`·
`caption_pages`·`continuation_of`·`entries[]`(`label`·`printed_label`·`description`·
`specimen_number`)를 쓰고, 전체에 `notes`·`skipped`·`pages_consulted` 를 붙인다.

저장된 link 응답 156건(출력 214만 토큰, 09-23 시점 `figure_ws` 에 남은 것)의 원문을 문자 수로 나누면:

| 구성 | 비중 |
|---|---|
| 캡션 전문 (`caption`) | 27% |
| 항목별 설명 (`entries[].description`) | 31% |
| 라벨·인쇄 라벨·표본번호 | 2.5% |
| `notes` | 1% |
| JSON 구조 (키 이름·따옴표·괄호) | 16% |
| 공백·줄바꿈 (들여쓰기) | 22% |

사고(reasoning) 토큰은 출력의 5.6% 로 작다. 눈에 띄는 것:

1. **같은 텍스트를 두 번 쓴다.** 캡션 전문을 옮긴 뒤 그것을 잘라 항목 설명으로 다시 쓴다(27% + 31%
   의 대부분이 같은 내용). Astra 는 묶음 주석("Tous ces individus sont représentés par le moule
   interne…")을 항목마다 되풀이해, 설명이 원문보다 길어지기도 한다.
2. **내용 없는 몫이 38%.** 모델이 JSON 을 들여쓰기해서 쓰고, 항목이 수백 개면 `"description"`·
   `"printed_label"` 같은 키가 수백 번 반복된다.

문자 비중과 토큰 비중은 다르다 — 공백은 토큰으로 싸게 묶이는 편이라 실제 절감은 문자 기준보다 작다.
그래도 **캡션 전문을 다시 쓰지 않게 하는 것**(항목 설명만 쓰게 하거나, 캡션은 쪽 번호·범위로만
가리키게)이 답 길이를 크게 줄여 stall 을 줄일 수 있는 가장 큰 여지다.

다만 이것은 **프롬프트·스키마 변경이라 클라이언트가 결정할 일**이다. PaperMeister 는 캡션 전문을
`Figure.caption` 으로 저장하고, `validate_link_result` 가 그것을 쪽 텍스트와 대조해 검증한다.
전문을 빼면 그 저장과 검증을 다른 방식(예: 항목 설명을 이어 붙여 복원, 또는 쪽 텍스트에서 범위로 잘라오기)으로
바꿔야 한다. 프롬프트가 바뀌면 `prompt_version` 이 바뀌어 기존 결과가 전부 다시 due 가 되는 점도 함께 따질 것.

## 6. 구간 형식 A/B 시험 (2026-09-29)

### 먼저 — 정밀 측정 (o200k 토크나이저, link 응답 400건 · 항목 23,919)

- 출력 토큰의 **88.6% 가 최종 JSON**, 사고 토큰은 5.5%. 소요 ≈ **94 s + 1k 출력 토큰당 33.5 s (r = 0.96)**.
- 항목 설명 구절의 **89% 가 캡션에 글자 그대로** 있다. 설명의 32% 는 앞 항목과 같은 머리말(종명 등) 반복.
- 캡션 줄은 OCR 텍스트에 그대로 있는 것이 48% 뿐 — 모델이 OCR 을 고치고 줄을 잇는다. 캡션을 OCR 참조로 대신할 수는 없다.
- panels 는 평균 95 s 중 출력 852 토큰(JSON 472). 출력이 작은 절반도 76 s — 고정비가 지배해서 출력 간소화 효과는 작다.

### 시험 방식

지시문 끝에 "구간 형식"을 덧붙여, 모델이 캡션을 **조각으로 한 번만** 쓰게 했다(한 줄에 한 조각, `x`/`h1`/`h2`/`e <labels>`/`t`,
선택 필드 `s=`·`p=`·`d=`). 스크립트가 캡션(조각 이어 붙이기)과 항목 설명(열린 머리말 + 자기 조각 + 꼬리말, 또는 `d`)을
원래 스키마로 복원한다. 크기가 고른 link 10건(출력 1.5k–27k 토큰, 모두 다른 논문)을 운영과 같은 codex 명령·작업 폴더로
다시 돌려, 같은 항목의 운영 답(A)과 비교했다. 스크립트와 결과는 세션 scratchpad `ab/` (build · expand · compare).

### 결과

| | A (지금) | B (구간 형식) | B/A |
|---|---|---|---|
| 소요 (9건, 아래 1건 제외) | 4,216 s | 3,138 s | **74%** |
| 출력 토큰 | 104k | 68k | **65%** |
| 최종 JSON 토큰 | 93k | 54k | **58%** |
| stall | — | 0 | |

- 복원 결과 10건 모두 **원래 스키마 통과**, 파싱 경고 0.
- 효과는 항목마다 다르다: `bfa5311d`(18k → 9k 토큰) 644 → 396 s, `decfd5c7`(27k → 14k) 972 → 552 s. 반면 `a09c77c7`(96%)는
  `d=` 예외 텍스트를 85번 써서 거의 줄지 않았고, `bc79da3f`(99%)는 JSON 은 12k 로 줄었지만 시간이 그대로였다.
- **`13e3464c` 는 B 가 10개 도판을 전부 skipped** — 설명이 있는 180–181쪽을 열지 않았다(A 는 찾음). 형식 탓인지 탐색의 회차별 차이인지
  1회로는 가릴 수 없다. 시간 비교에서는 뺐다.

### 품질 차이 — 형식을 다듬으면 고칠 수 있는 것들

1. **인쇄 라벨이 설명에 섞인다** ("Figs. 1-5 Cybele punctata", "(a) an open woodland…", "1. Bathyuriscellus…"). 캡션을 원문 그대로
   조각낼 때 라벨 글자가 조각에 남기 때문. → 조각에 "캡션에는 넣고 설명에서는 빼는" 라벨 접두 필드를 둔다.
2. **라벨 없는 단일 그림의 관례가 A 안에서도 갈린다** — 어떤 논문은 항목 1개(`"1"`), 어떤 논문은 0개. B 도 논문마다 달랐다
   (`decfd5c7` 66개 도판에서 1 → 0, `bfa5311d` 7개에서 0 → 1). 형식 설명에 한 가지로 정해 두면 된다.
3. **꼬리말 범위 오용**: "The figures marked + are magnified 3 times" 를 모든 항목에 붙였다(표시된 것에만 해당). → 조건부 주석은 `x` 로 두게.
4. **표본번호 표기**: B 는 "ИГиГ № 700/686", A 는 "700/686". 틀린 게 아니라 관례 차이 — 형식 설명에 적어 둘 것.
5. B 쪽 설명이 오히려 **원문에 더 충실한** 경우도 있다(A 가 뺀 "зона B. gurarii, разрез 11, слой 9" 를 B 는 유지).

### 판단

출력을 줄이면 시간이 준다는 것은 확인됐다(출력 65% → 시간 74%). 가장 큰 항목이 약 절반으로 줄어 stall 구간(15k+) 아래로
내려온다. 다만 지금 형식 그대로 운영에 넣을 수준은 아니다 — 위 1–4 를 반영한 v2 형식으로 같은 10건(+ `13e3464c` 재시도)을
다시 돌려 확인한 뒤, 복원 스크립트와 함께 **PaperMeister 에 제안**하는 순서가 맞다(프롬프트·스키마·검증은 클라이언트 몫).

## 7. 클라이언트에 전할 것

- 답 줄이기(§5): 캡션 전문을 다시 쓰지 않는 스키마를 검토할 만하다 — 저장·검증 방식 변경과 전면 재due 를 함께 따질 것.
- `failed` 4건(`78fef4fc` 3/5, `79fa0b44` 1/8, `32f87220` 2/2, `e0837de8`)은 **더 잘게 나눠 재제출**.
  서버 resume 은 하지 않는다.
- 대기열에 도판 80개짜리 항목이 12개, 47–69개짜리가 몇 개 있다. 본문 그림 위주라 항목당 내용이
  적을 수 있지만, 답이 15k 토큰을 넘을 만하면 미리 나누는 편이 낫다(09-18 실측: 출력 5k 미만
  실패 0건, 15k 초과 18건 중 5건 실패).
- `figure_queue.py` 의 `--max-queue 120` "≈ 12시간"은 항목당 6분 가정. link 실측은 13–25분이라
  120항목이면 30–50시간이다.
